# Contributing

Keep changes narrow, tested, and traceable to a concrete STAC or geospatial behavior.

For the current hardening scope, read [docs/HARDENING_ROADMAP.md](docs/HARDENING_ROADMAP.md) before starting work.

## Workflow

For non-trivial changes:

1. Start from the current `main`.
2. Create a narrowly scoped branch.
3. Link the change to an issue or a specific hardening-roadmap item.
4. Add or update tests before changing behavior where practical.
5. Run the full local quality gate.
6. Open a pull request; do not use direct commits to `main` for hardening work.
7. Merge only after required CI checks pass.

While the project has a single maintainer, repository rules should require pull requests and CI but should not require an impossible self-approval. Independent review should become required when a second maintainer is available.

## Local checks

Run all of these before requesting merge:

```bash
ruff check .
ruff format --check .
mypy
pytest --cov=stac_scout --cov-report=term-missing
python evals/runner.py
python -m build
```

If you intentionally reformat code locally, run `ruff format .` before the check-only command.

## Correctness conventions

- Prefer small pure functions for normalization, identity, task derivation, constraint evaluation, and verification logic.
- Keep provider quirks behind catalog adapters.
- Keep provider and task registries declarative and packaged with the library.
- Do not add a dependency when the standard library is sufficient.
- Do not make recommendation logic depend on prose generated by a model.
- Represent unavailable metadata as UNKNOWN rather than guessing a value.
- Do not silently collapse probable cross-provider duplicates.
- Do not silently ignore a public hard constraint.
- Hard constraint failures must not be overridden by ranking or preference scores.
- A new task rule must distinguish required from preferred inputs, include rationale, cite authoritative sources where available, and add an evaluation case.
- Task rules must not invent event dates, comparison windows, or sampling cadence.
- Geospatial behavior must state CRS, geometry, longitude-wrapping, and resolution assumptions where they affect correctness.
- Raster planning must distinguish categorical/mask data from continuous data when selecting resampling.
- Provider failures must not hide unexpected internal programming errors.
- Provenance changes must preserve enough information to interpret replay results.

## Tests and evals

A coverage percentage is a floor, not proof of correctness.

For bug fixes, add a regression test that fails before the fix and passes after it.

For changes that affect dataset decisions, identity, task derivation, constraint semantics, geometry, asset selection, or replay behavior, add or update deterministic eval cases as appropriate.

Test success, failure, and ambiguity/UNKNOWN paths where all three are meaningful.

Remote provider state belongs in live checks rather than deterministic CI unless the test is explicitly isolated and documented.

## Pull request scope

A pull request should be reviewable as one argument.

Avoid combining:

- correctness fixes with unrelated refactors;
- provider-specific changes with generic abstractions unless the abstraction is required;
- release automation with scientific-semantic changes;
- large documentation rewrites with behavior changes that are still moving.

If follow-up work is discovered, open or link an issue instead of expanding the PR indefinitely.

## Security

Follow [SECURITY.md](SECURITY.md).

Never commit credentials, access tokens, signed URLs, private endpoints, or sensitive provider responses.

Changes that introduce or modify external network I/O must document timeout behavior, error boundaries, redirect behavior where relevant, and hosted-deployment trust implications.
